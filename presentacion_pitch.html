🔍 Problema y Necesidad

El problema

  • Los hospitales colombianos operan con sistemas aislados
  • No existe una red unificada para compartir historias clínicas
  • Los pacientes deben repetir exámenes y datos en cada institución
  • Riesgo de errores médicos por falta de información completa
  • Dificultad para garantizar continuidad del tratamiento

¿A quién afecta?

👤 Pacientes

Pérdida de continuidad en su atención médica al cambiar de institución

🩺 Profesionales de salud

Decisiones clínicas con información incompleta del paciente

🏥 Instituciones

Duplicación de recursos, exámenes y costos operativos

Funcionalidades principales

  • Registro y aprobación de hospitales en la red
  • Gestión de usuarios con roles diferenciados (RBAC)
  • CRUD de historias clínicas electrónicas
  • Registro de pacientes con consentimiento informado

  • Sistema de notificaciones al paciente
  • Registro de condiciones crónicas / antecedentes

🏗️ Estilo Arquitectónico: Microservicios

Descomposición modular progresiva con API Gateway como punto único de entrada.

Justificación técnica

  • Escalabilidad: cada servicio escala según su demanda
  • Aislamiento de fallos: un fallo no afecta al resto
  • Autonomía de datos: cada servicio tiene su propia BD
  • Independencia de despliegue: actualizaciones sin downtime total
  • Interoperabilidad: APIs REST estándar para cada dominio

Comunicación inter-servicios

Al crear una historia clínica, el EHR Service:

  • 1. Valida paciente → Patient Service
  • 2. Genera PDF → ReportLab
  • 3. Registra auditoría → Audit Service
  • 4. Notifica paciente → Notification Service

⚖️ Decisiones Arquitectónicas Principales

Decisiones tomadas

BD por microservicio

Beneficio: aislamiento total de datos
Trade-off: no hay joins entre servicios

JWT compartido vía common/security.py

Beneficio: autenticación descentralizada
Trade-off: misma SECRET_KEY en todos

Separación Frontend / Backend

Beneficio: SPA + APIs independientes
Trade-off: mayor complejidad de CORS
